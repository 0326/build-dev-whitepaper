# 质量验收

先验证文章是否有用且可信，再验证它能否正常到达读者。以证据判定通过、需修改或阻塞，不靠篇数、字数、综合分数抵消关键缺陷。

## 内容检查

| 检查项 | 可接受的证据 | 需要修改的表现 |
| --- | --- | --- |
| 读者与问题 | 本文主问题清晰，读者能做出具体判断 | 标题是模块名，正文只有功能枚举 |
| 递进关系 | 前置概念有解释或链接，下一篇承接新问题 | 使用未定义术语；每篇重讲总览 |
| 独立深度 | 核心机制有具体过程、责任、关键状态或不变量 | 拆成多篇后仍只剩一两段摘要 |
| 设计取舍 | 解释选择原因、代价和适用条件 | 只写优势；把部署建议当内建保证 |
| 失败与边界 | 给出与本文问题有关的失败、限制或未知 | 跳过失败路径；把推断写成已实现 |
| 可追溯性 | 关键主张对应同版本的具体文件、符号或测试 | 只有仓库首页链接或一长串 sources |
| 版本一致 | 正文、示例、图表、引用和迁移说明同基线 | 新版图配旧版正文；复制快照后只改版本号 |
| 附件权威 | 术语定义一致，产品规范和编辑约定分开 | 附件自创上游 MUST；术语前后不同 |
| 独立读者测试 | 无作者上下文的读者能回答定位、机制、选择、失败和证据问题 | 只由作者自审，或读者把未知误读成保证 |

按文章类型调整：阅读指南不必硬写内部状态机，术语表不必伪造失败路径，但机制文章不能用“它很灵活”代替机制说明。

审读核心机制文章时，尝试回答：一个真实输入经历了什么？谁负责每一步？哪一步可能失败？哪些保证来自哪一版实现？读者如何据此选择或排错？不能回答的地方优先补证据或缩小论断。

按 [独立读者测试](reader-testing.md) 运行文章快照，保存逐题答案、证据和误解。关键机制、边界或证据问题答错时，文章保持 draft 或 blocked，直到修订并重测。

对比相邻文章的主问题、独有信息和示例。若删去其中一篇几乎不损失信息，应合并或重新划分，而不是补无关段落凑长度。

## 工程检查

仅检查本轮涉及的交付形态，优先跑现有验证命令。

| 层次 | 检查 | 不能据此推断 |
| --- | --- | --- |
| 内容数据 | schema、稳定 ID、导航覆盖、版本、附件与来源登记 | 文章已讲透、来源支持结论 |
| 固定来源 | ref → commit、引用文件 / 符号在基线存在 | 所有外链可达、主张一定正确 |
| 图表 | 源码解析、产物更新、正文引用、实际展示 | 架构语义正确 |
| 示例 | 指定环境执行与输出比对 | 其他版本或部署环境也成立 |
| 页面 | 构建、路由、链接、导航与改动涉及的视图 | 视觉和键盘交互自动合格 |

检查未运行要写原因；失败要写实际错误与影响。不存在本地源码或渲染环境时，不把假数据、占位图或仅检查文件存在作为替代证据。

## 严重问题与状态

- **阻塞发布**：关键事实无依据或矛盾、版本混用、失效入口、误导性安全 / 性能保证、将缺失检查写成已通过。
- **需要修改**：文章重复、主问题未答清、关键失败路径未解释、规范权威不明、必要附件缺失。
- **可记录后续**：非必要导出格式、进一步的视觉润色、未在本轮范围内的可选设施。不要让这些事项拖住已授权的交付。

草稿可以带清晰的未知与待核验项；将它标为草稿并继续完成可做部分。未解决阻塞项时不能将内容宣称为已验证或已发布。

## 交付说明

优先使用项目现有记录格式，至少让用户看见：

1. 交付了什么、位于哪里，以及对应的资料基线。
2. 哪些结构或内容变化解决了哪个阅读问题。
3. 实际完成了哪些内容 / 工程核验，具体结果如何。
4. 哪些检查未做、哪些结论仍有限制，以及后续处理条件。

最终回答先给成品入口与最重要变化，具体命令和逐条证据放在可审阅的交付记录中。不要把计划、模板或初稿称为完整白皮书。

## 方法自检场景

维护此 skill 时，可用不同规模项目检验它是否过度依赖 DSH：

- 小型库，仅一个稳定版本，已有 Markdown 文档：能否形成简洁阅读路径，而不强行建五组、版本站点或 CI？
- 有 RC 与稳定版的平台，官方源码可访问：能否锁定不同基线并据差异决定文章、图和附件的更新？
- 资料受限或来源互相矛盾的协议：能否完成有用的草稿并明确收敛结论，而不伪造权威规范？

对方法的验证和对真实项目的验证分别记录；合成案例通过不能证明真实项目白皮书内容正确。

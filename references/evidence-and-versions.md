# 证据与版本规范

## 来源与结论

默认仅从项目官方仓库、官方发布与文档获取目标项目事实；内部项目使用用户提供或授权的第一方材料。用户可调整来源策略，但始终区分来源层级和结论的置信范围。

Manifest 中将来源身份、版本锁和文章证据拆成三个层次：顶层 `sources` 只登记来源；版本 `source_locks` 固定 ref、commit 或网页访问时间；文章 `evidence` 绑定具体路径、符号、章节、URL 和稳定 evidence ID。关键事实、推断、建议和未知可进一步登记为 `claims`，避免一串 sources 被误当作整篇文章的证明。

建立显式来源注册：来源 id、所有者 / 仓库、可读 ref、不可变 commit、官方文档位置和核验时间。网页无法绑定版本时记录访问时间与适用范围，不把滚动文档当成旧 tag 文档。

核实来源 URL 的 host 和仓库路径边界，不能只做字符串前缀匹配。GitHub 仓库 abc 与 abc-extra 不是同一来源。

| 主张 | 优先核对 |
| --- | --- |
| 定位与非目标 | 官方 README、架构设计和已发布说明 |
| 运行行为 | 固定 commit 下公开接口、调用链和相关测试 |
| 安全 / 持久性 / 并发保证 | 所有权、失败路径、测试与正式契约 |
| 兼容性和变化 | Release / migration 文档及两端官方 diff |
| 性能或评测优势 | 基准方法、硬件、数据集、配置、重复次数和原始结果 |
| 采用建议 | 已核实约束，加明确标注的工程判断 |

README 和代码不一致时记录差异，核对目标版本实际入口；缺少明确证据时收窄结论。不能把“未找到实现”写成“项目绝不支持”。版本号是 RC 也不意味着每项能力都被官方称为实验。

## 论点证据记录

建议使用轻量表或现有元数据；小修订只记录变更涉及的主张，不制造全文审计开销。

| 主张 id | 文章 / 段落 | 主张 | 类型 | 官方路径与符号 / 章节 | 来源 commit | 限制 / 待核实 |
| --- | --- | --- | --- | --- | --- | --- |
| runtime-owner | 运行机制 | 谁拥有写权限 | fact | 源码所有者类型 + 失败测试 | 固定 SHA | 仅当前运行模式 |

核心因果链、安全边界、可靠性保证和迁移结论应能沿这张表复核。每篇仅挂一串 sources 或 evidence 不能覆盖没有支撑的段落。

标签含义：
- **fact**：官方资料明确支持；
- **inference**：由已核实事实推导，写明推导和限制；
- **recommendation**：作者建议，不能归于官方；
- **unknown**：证据不足，不作为已验证结论发布。

编写白皮书自己的阅读约定无需虚挂产品 README 证明该约定。明确其 authority 是 document-policy；上游规范则使用 upstream-contract。

## 复用开源写作方法

只读足以解决当前缺口的参考项目：
- Handbook / Book：阅读路径、章节递进、独立文章与附件；
- Specification：规范语言、生命周期、兼容性与精确概念；
- 架构手册：设计理由、替代方案、状态所有权；
- 工程论文或评估文档：可复现实验、基线与限制。

记录“参考的具体文件 / 页面、适用模式、目标项目缺口、采用的改动”。社区项目的排版结构可以被借鉴；其中关于目标项目的技术说法仍需回到第一方证据重新核验。

不在目标白皮书中塞入一篇竞品报告。对标记录可作为本次评审交付或维护备注。

## 完整快照

快照绑定：正文、导航、示例、图源码 / 渲染资产、来源链接、术语、限制和迁移说明。可以物理复制，也可以用可复现的版本映射；关键是读到的所有内容来自明确且一致的基线。

按项目约定筛选版本。若约定 RC + Stable，先过滤通道，再创建任务或文档；被排除版本不应成为隐藏快照。若项目只支持稳定版或 LTS，不擅自扩成 RC 策略。

区分：
- upstream_latest：按策略检测到的上游版本，可以尚未有文档目录；
- latest_published：已通过约定门禁并发布的白皮书快照；
- documentation_revision：同一个上游基线的文档修订次数。

发现新版只更新检测状态或待办，不能直接改变 latest_published。latest 是入口别名，引用与 canonical 使用具体版本。源码链接优先使用固定 commit；若保留 tag 链接，也要记录并校验其解析 SHA，不能假定 tag 永远不移动。

## 将不同状态分开

| 维度 | 示例 | 说明 |
| --- | --- | --- |
| 上游通道 | stable、rc、lts | 来自发行策略 |
| 能力成熟度 | experimental、deprecated、unspecified | 来自官方能力说明；不猜测“stable” |
| 内容核验 | draft、reviewed、blocked | 文章事实是否被核实 |
| 发布状态 | unpublished、published | 是否已通过本项目发布流程 |

实验能力可以被完整核验；已发布页面也可能需要纠错。不要用一个 status 同时表达这些维度。

## 更新和纠错

1. 解析新 ref 到 commit，保留旧锁定值。
2. 生成官方 diff，识别公开接口、入口、默认组合、配置、协议、UI 和迁移差异。
3. 从“文章 → 来源路径 / 符号”反查受影响文章；依赖、默认值或跨层契约变化要扩展检查，不能只按文件名过滤。
4. 复用未变内容时仍核对来源锁与契约；机械替换版本号不能算验证。
5. 逐版本重建投影并检查正文、图和来源一起切换。
6. 缺少相同文章时给出明确的版本内回退，不静默显示别的版本内容。
7. 旧版事实错误可原基线修订并记录原因；禁止把新版本行为补进旧版。
8. 无迁移证据时不宣称“零 breaking change”或“无需迁移”。

无法获得官方资料时，交付能完成的结构和缺口记录，保留 draft / blocked，说明具体缺失证据与影响。不能用社区内容补洞后继续标 reviewed。

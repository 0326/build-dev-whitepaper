# 工程与维护

仅在涉及站点、版本更新或工程验收时使用。纯内容评审不要求搭建站点、添加依赖或引入本节全部设施。

## 先复用，再补缺

查找当前内容格式、导航模型、路由、构建命令、图表工具、测试和部署约定。保持用户已选择的工具链；React、Vite、Markdown、MDX、静态生成或单文件发布都不是白皮书质量的前提。

单篇 Markdown 可以用相邻链接和目录实现阅读路径。较大站点再增加两级左栏、页内目录、版本选择和搜索。每项设施都应解决一个具体阅读问题。

## 受维护数据与生成结果

选取现有 frontmatter、清单或内容集合中的一个作为事实源，从它生成：

| 受维护信息 | 应保持一致的结果 |
| --- | --- |
| 文章 ID、标题、分组、顺序 | 菜单、前后篇、首页目录 |
| 版本与发布状态 | 默认入口、版本切换、搜索筛选 |
| 官方来源 ID、ref、commit、文件路径 | 就近证据链接与来源索引 |
| 图源码与渲染资产关系 | 页面插图、打印版、导出包 |

不要用第二份手工数组修补导航。文章 ID 应稳定；更改路径时按现有站点能力添加重定向或迁移提示。

版本切换先尝试相同文章 ID。目标版本没有该文章时，给出明确说明并回到该版本目录；不要悄悄打开另一个版本的正文。分组顺序属于当前快照，不能总读最新版本的注册表。

## AI 与 CI 的分工

AI 做资料阅读、概念解释、取舍论证、文章去重、变化影响分析和语义评审。脚本做可重复的版本发现、差异收集、结构验证、构建、链接及资产检查。

更新流程依次是：发现符合策略的新基线 → 锁定 ref 与 commit → 收集变化证据 → 映射受影响的文章和附件 → 撰写与评审 → 工程验证 → 按授权发布。检测步骤只能创建待处理任务或草稿，不能直接把文档置为已发布。

只为本轮授权的维护范围配置 CI、定时任务或发布动作。已有脚本能完成检查就复用；不要仅为一篇小修订新建测试框架。

## 图表、示例和页面

- 保存可编辑图源码；若提交 SVG 等产物，记录生成方式。检查源码能够解析、产物对应当前源码、页面能够显示，三项不是同一件事。
- 语义评审核对责任边界、箭头方向、同步 / 异步和失败路径；渲染工具不能替代它。
- 示例记录环境、版本、输入与预期输出。可运行示例用项目现有命令验证；未执行则明确标注。
- 布局或交互有改动时检查深链接、刷新、版本切换、窄屏导航及键盘可用性。任务包含打印或 PDF 时才检查相应输出。
- 外链访问失败要区分缺失、权限与网络故障。没有访问条件时报告未核验，不把 HTTP 可达性当成内容正确性。

## 可选的离线结构审计

`scripts/audit_snapshot.py` 读取一个 JSON 文件，输出 JSON 检查结果。它只读、不联网、不安装依赖，适用于以 Git 文件为证据的快照。官方网页、PDF 或内部非 Git 资料沿用项目检查方式，不为适配工具编造 commit。退出码 `0` 表示所执行的结构检查无错误，`1` 表示发现错误，`2` 表示命令参数有误。

**审计输入是现有数据的临时导出，不是另一个要长期维护的内容注册表。** 有现成且等价的项目校验工具时可以直接使用它，不必再导出。示例见 [审计输入](../assets/audit-input.example.json)，相对路径以输入文件位置为基准。

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 当前为 `1`，仅是审计输入格式版本 |
| `project`, `version` | 项目名称、该快照的基线标识；无正式版本时可用锁定 commit 的快照名 |
| `release_channel` | 项目自定，例如 stable、rc、snapshot；工具没有 DSH 默认通道 |
| `publication_state` | 此导出的发布状态：draft 或 published |
| `policy.allowed_release_channels` | 当前项目允许的通道，至少一个 |
| `policy.expected_body_groups` | 可选，仅在项目已约定分组数时填写 |
| `policy.required_appendices` | 必备附录的文章 ID，可为空数组 |
| `roots.content`, `roots.assets` | 本快照正文与图资产根目录；没有图时不要求资产目录存在 |
| `sources` | 来源注册表；每项含唯一 `id`、`repository`、`ref`、完整 40 或 64 位 Git `commit` |
| `groups` | 分组项含 `id`、`title`、`kind`（body / appendix）、有序 `articles` ID 数组 |
| `articles` | 每篇含 `id`、`slug`、`title`、`file`、`version`、`verification`、`authority`、`sources`、`diagrams` |

`articles[*].verification` 为 draft 或 reviewed，表示编辑核验状态，不表示产品能力稳定性。已发布的导出要求全部 reviewed；**工具读取这个声明，不替作者完成核验**。项目自有的 blocked 等未核验状态只能映射到 draft；保留原始阻塞记录，不能借格式转换提升核验状态。

`authority` 为 `upstream` 或 `document-policy`。解释项目能力、引用 upstream-contract 的文章用 upstream 并至少给出一条来源；白皮书阅读约定等编辑政策可用 document-policy。混合文章只要包含项目能力主张，就按 upstream 导出。

文章 `sources` 中每项为 `{"source":"core","path":"docs/architecture.md"}`；`diagrams` 是相对资产根目录的文件路径数组。图源码与产物是否一致仍由项目工具检查。

运行：

```bash
python3 <skill-dir>/scripts/audit_snapshot.py /path/to/audit.json
python3 <skill-dir>/scripts/audit_snapshot.py /path/to/audit.json \
  --upstream core=/path/to/official-checkout
```

第二种方式对来源 `core` 在本地 Git 对象库核验 commit、ref 绑定及被引用路径是否为文件；不要求工作区 HEAD 指向该版本，也不读取未提交的源码冒充固定版本。多个来源可重复使用 `--upstream`。仓库不含所需 ref 或对象时报告错误，不自动拉取。

工具检查分组和文章 ID 唯一、每篇只被导航引用一次、文章 / 图文件存在、元数据版本一致、声明的发布规则、来源登记和相对路径。它不解析正文 frontmatter；导出过程应读取项目实际有效元数据，包含继承的版本字段。

没有提供官方 checkout 时，来源内容及 ref 绑定检查记为跳过。工具也不判定仓库是否官方，不验证自然语言、来源是否支持结论、正文中的链接、Mermaid 语法、生成产物新鲜度或浏览器渲染。报告这些限制，不能把结构通过写成“白皮书全面验证通过”。

## 交付与持续维护

把可复现命令、实际结果和未验证项放入已有贡献说明或交付记录，不在每篇文章复制工程细节。正文更新、修订记录和来源索引一起交付。下一次维护从受影响的结论出发，不能只更新版本号。

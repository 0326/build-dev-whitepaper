# 内容设计与写作

## 从读者任务建立目录

用一个句子回答“读者看完要作出什么技术决定”。常见任务包括评估是否采用、理解主链路、开发扩展、产品集成、诊断故障、升级迁移。指定主读者，其他角色使用阅读路径进入，不让每篇都重新科普基础概念。

目录按概念依赖排序：
1. 问题、定位、设计目标与非目标；
2. 核心模型与端到端运行过程；
3. 能力、机制和设计取舍；
4. 扩展、集成或部署；
5. 可靠性、边界、迁移与演进；
6. 术语、约定、契约和来源索引。

这只是覆盖面示例。数据库可能按写入、查询、复制、恢复组织；协议可能按实体、生命周期、传输、兼容性组织；小型库可合并为少量文章。遵守用户确认的分组约束，不能在通用检查器里写死“必须五组”。

入口页说明本白皮书的实际阅读价值，例如固定版本、关键机制追踪或职责边界；没有具体对标证据时不要宣称优于其他文档。

## 文章卡决定是否应该拆篇

| 字段 | 实际用途 |
| --- | --- |
| 稳定 id / slug | 在重排、改名和版本切换后仍能定位相同主题 |
| 主问题 | 限定一篇文章的解释范围 |
| 前置概念 | 避免跳步，不按源码文件数量机械拆分 |
| 可执行判断 | 读完能选择方案、定位责任或排查问题 |
| 独有机制 / 场景 | 确保拆分后内容有增量 |
| 证据 | 关联接口、调用链、状态、测试或官方设计 |
| 不覆盖内容 | 把接口全集留给 Reference，把重复解释留给关联文章 |
| 关联文章 | 用具体链接形成顺序和分支路径 |

若两个子项回答同一个问题、复用同一场景和同一结论，应合并或重新定义职责。若一篇需要两套互不依赖的生命周期和失败处理，应拆篇，并保留短选择页。

## 文章的解释深度

技术机制文章应使读者看懂：
- **问题与前提**：缺少该机制会发生什么，何时适用；
- **职责与所有权**：谁持有状态、谁授权、谁写入、谁释放；
- **一次实际过程**：从入口到结果的重要变化，以及控制 / 数据流；
- **设计理由与取舍**：本方案在哪些约束下成立、代价是什么；
- **失败与限制**：失败发生在哪一层，能否恢复、由谁补足保证；
- **落地判断与证据**：开发或接入时选什么边界，去哪验证。

不强制字数、代码数量或每篇配图。来源缺少设计理由时，不把自己的推测归于作者：写成明确推断或省略，附可核验边界。

### 拆分的反例

选择页已有“后台任务有 id、所有者和完成通知”；独立后台任务文章仍只有这三句话，加“何时使用 / 设计建议”两个标题。这只是重复概述。

### 有增量的机制文章

沿一个后台导出场景解释：入口如何注册、调用方何时返回、所有者如何读取结果、取消如何传递、资源由谁释放、进程重启后的保证由哪层提供。每个技术结论都回到目标版本的公开接口或测试；官方未说明重启语义时写“未核实”，不能推定持久或不持久。

选择页保留比较维度与跳转；机制细节归属单篇，不再复制回选择页。

## 区分文档类型

| 类型 | 应承担的内容 | 避免 |
| --- | --- | --- |
| 白皮书正文 | 模型、原理、取舍、限制及决策依据 | 目录式 API 清单、没有因果的术语串 |
| 教程 / 示例 | 完成一个具体任务的步骤与可观察结果 | 取代所有架构解释 |
| Reference | 精确接口、字段、事件、配置与状态 | 在多个正文中手写相同接口全集 |
| 规范 / 约定 | 来源、适用范围、约束级别、兼容规则 | 把建议升级成上游强制标准 |
| 索引 | 概念到权威文档 / 文章 / 符号的映射 | 整篇重复“扩展地图” |
| 迁移说明 | 旧行为、新行为、影响、动作、验证 | 仅转载 Release 列表 |

对标 Handbook、Book、Specification 或论文时，按这些类型取长处。不要因参考项目有教程就把本任务改成入门课程。

## 附录安排

- **术语表**：统一中英文、定义、易混概念和正文入口。不要循环定义。
- **阅读与编辑约定**：读者需理解的证据标记、版本范围、事实 / 推断 / 建议。流水线细节归维护文档。
- **产品契约或规范**：明确官方出处及版本；若是本白皮书约定，直接标注其作用域。
- **来源索引**：按问题映射官方路径；能从元数据生成就不手写第二份。
- **按需附件**：能力表、事件时序表、配置索引、兼容矩阵、迁移表。没有需求与证据时不凑数量。

## 语言、图表与示例

开头直接给核心结论和范围。段落只推进一个问题；首次术语给最短精确定义，此后沿用。避免“深入探讨、赋能、强大灵活、不是 X 而是 Y”等填充，以及与真实边界不符的比喻。

图只表达一类关系：架构依赖、事件顺序、状态迁移或数据所有权。方向一致，节点名称与正文一致，超过可读宽度就拆图；不要拿流程图代替设计论证。小型线性关系可直接写文字。

示例标出版本、必要配置、输入与预期可观察结果。只验证模型自报“成功”不充分；有实际执行时应核对文件、事件、响应或其他外部结果。未执行时如实说明。

# DSH 示例：从一次改版提炼可迁移方法

这是 2026-09 的 DSH 白皮书讨论与改版案例，不是当前 DSH 功能或最新发布状态的保证。继续执行 DSH 任务时重新核对仓库与上游官方版本。

## 案例约定

- 目标仓库：0326/dsh-plugin-market；目标技术来源：deepseek-ai/deepseek-harness。
- 当时基线为 v0.1.5-rc.1，同时维护 rc.2 快照；同步仅关注 RC 和正式版。
- 左侧采用五个正文分组加“附录与规范”，每个子项独立成篇，目录只显示序号和标题。
- 技术事实只能来自官方；Electricitysheep/dsh-handbook 用于观察阅读组织方式。
- 版本切换要求正文、目录、图和官方源码链接整体切换。
- 使用 Markdown 和结构化架构图；文风深入浅出、简明，不使用空泛解释。
- Action 执行确定性工程任务，AI 负责阅读、写作和迁移分析。

## 可迁移与不可机械复用

| 案例选择 | 可迁移理念 | 其他项目怎样调整 |
| --- | --- | --- |
| 五组正文 | 按学习依赖分层 | 由项目规模与读者决定组数 |
| RC + 正式版 | 显式版本纳入策略 | 可改稳定版、LTS 或协议版本 |
| nav 驱动侧栏与构建 | 元数据有单一来源 | 沿用现有文档框架和 schema |
| 拆开 Subagent / Workflow / Jobs | 每篇回答一个有独有机制的问题 | 按目标系统的职责和生命周期拆篇 |
| 术语、规范、索引附件 | 解释与查阅分离 | 增补目标项目实际需要的契约与速查 |
| 固定 tag 与 SHA | 事实可复现 | 更推荐 commit 链接或校验 tag 解析值 |

## 需要避免重演的问题

- 拆出独立文件，却重复原比较页的摘要：使用文章卡验证独有的机制、场景与边界。
- 两个版本的新增文章完全相同，只改版本号：先核实源文档与契约，再决定是否复用。
- 将“五组”写进通用校验器：分组数只能来自项目策略。
- 将实验成熟度与已核验状态混在同一个字段：分开表示。
- 只验证 Mermaid SVG 存在：还要按需要验证语法、资产新鲜度和页面可读性。
- 构建成功就宣布完整完成：准确记录未执行的浏览器验证或环境受限检查。
- 在每篇侧栏挂通用 README，却没核实关键保证：定位到具体文件、符号、测试或官方设计。
- 新旧方案冲突：采用用户最新约定及现行发布策略，不让早期 alpha / next 设计重新生效。

## 如何参考

DSH 场景用于校验“这套方法能否保持证据与版本一致”；另用一个小型库或数据系统检验“会不会强行套用 Agent、五组目录或 RC”。两种场景都成立，才说明 skill 有通用性。

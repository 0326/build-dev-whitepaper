# SQLite 回滚模式如何实现原子提交

> 本文是 build-dev-whitepaper 的标杆样稿，用来展示前提、一次完整过程、崩溃路径和测试证据。它只解释 SQLite 官方原子提交文章描述的回滚模式。

## 这篇文章要回答的问题

硬件不能同时写入数据库事务涉及的所有磁盘扇区，SQLite 为什么仍能让事务表现为“全部发生或全部不发生”？读完后，读者应能定位原子提交依赖的前提、日志文件的作用，以及电源故障后恢复发生在哪一步。

## 先给判断

SQLite 回滚模式把旧页面先写入回滚日志，再写入数据库文件。提交完成的标志不是“每个页面都能瞬间写完”，而是恢复逻辑能够根据日志判断：事务已经完整提交，或应把未完成写入恢复成提交前状态。

因此，原子性是数据库文件、回滚日志、锁和持久化顺序共同提供的性质。它依赖底层存储和文件系统满足文档列出的假设。

## 前提决定保证范围

官方文章将存储写入抽象为扇区，并讨论不完整写入、写入顺序和磁盘刷新。SQLite 需要知道在这些情况下，回滚日志和数据库页能够被识别和恢复。

本文不把这些假设推广到所有文件系统，也不把回滚模式的步骤当作 WAL 模式的实现。官方页面明确指出，启用 WAL 时原子提交采用另一套机制。

## 一次提交过程

以下过程沿官方文章的回滚模式章节展开：

1. 连接获得读取锁并读取数据库中的页面。
2. 事务取得保留锁，阻止其他连接开始写入。
3. SQLite 创建回滚日志，把将要修改的原页面和必要信息写入日志，并刷新日志。
4. 事务取得排他锁，在用户空间修改页面，然后把修改写入数据库文件。
5. 数据库文件刷新后，SQLite 删除或清理回滚日志并释放锁。

这里有两个关键顺序：旧页面必须在被覆盖前进入日志；日志必须在数据库修改前达到可恢复状态。删除回滚日志后，其他连接才会把数据库视为没有未完成事务。

## 写入中断时发生什么

如果进程或系统在数据库页全部写完前中断，重启后的连接会检查是否存在“热”回滚日志。若日志表明上一次写入没有完成，SQLite 获得必要锁，按日志中的旧页面恢复数据库，然后删除热日志，继续以事务未提交的状态运行。

如果数据库和日志都已完成提交，恢复逻辑不会把已提交事务错误回滚。原子性来自“提交标志的可观察顺序”和“失败后按日志重建旧状态”的组合。

## 测试如何支持这个结论

SQLite 官方文章说明，其崩溃测试使用修改过的 VFS 模拟电源故障、扇区不完整写入、垃圾数据和乱序写入。测试在不同写入时点反复中断事务，重新打开数据库后检查事务是否完整发生或完全没有发生，以及数据库是否保持一致。

这类测试比单次成功提交更能支持恢复结论，但它仍然是官方测试环境下的证据。部署方使用不同文件系统、存储设备或 VFS 时，需要重新核对假设。

## 取舍与边界

回滚日志需要额外写入和刷新，锁的范围也会影响并发。文档还讨论保留日志、截断日志和文件系统安全追加等优化；这些优化改变性能和清理方式，不能改变文章中声明的恢复前提。

本文没有描述 WAL 模式的具体提交过程。需要解释 WAL 时，应使用官方 WAL 文档建立单独文章，避免把两套机制拼成一个流程。

## 读者如何使用这个判断

- 遇到崩溃恢复问题时，先确认运行模式，再检查数据库文件、回滚日志和文件系统假设。
- 评估存储兼容性时，核对不完整写入、刷新和锁语义，不能只看数据库 API。
- 解释“事务已提交”时，区分页面已写入、日志已清理和连接已释放这些状态。

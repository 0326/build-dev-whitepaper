# 文章分型模板

白皮书中的每篇文章先选择一种主要类型，再按该类型组织内容。类型限制文章要回答的问题，不限制文章必须使用固定标题。

## 先选类型

| 类型 | 读者要完成的任务 | 文章必须交代 |
| --- | --- | --- |
| 概览与选型 | 判断是否采用、从哪里开始 | 问题、目标、适用范围、替代方案 |
| 机制解释 | 理解系统如何工作 | 模型、职责、过程、不变量、失败路径 |
| 设计取舍 | 理解为什么这样设计 | 约束、候选方案、选择依据、代价 |
| 实践验证 | 完成一次可观察的技术任务 | 前置条件、步骤、输入、结果、排错 |
| 版本迁移 | 从旧基线迁移到新基线 | 差异、影响、动作、验证、回退 |

一篇文章可以有辅助类型，但只能有一个主类型。文章卡的 type 应与正文的主要任务一致。

## 选择规则

- 读者在问“这是什么、适不适合我”时，使用概览与选型。
- 读者在问“它为什么能这样工作”时，使用机制解释。
- 读者在比较方案、评估成本或安全边界时，使用设计取舍。
- 读者需要把一个任务跑通并看到结果时，使用实践验证。
- 读者面对版本变化、兼容性或升级风险时，使用版本迁移。
- 如果一篇文章同时承担两个互不依赖的任务，拆成两篇，并通过前置概念和关联文章连接。

## 最小文章卡

创建正文前，先填写：

~~~yaml
id: stable-topic-id
type: mechanism-explanation
primary_question: "读者最需要回答的一个问题"
reader_outcome: "读完后能作出的判断或完成的动作"
prerequisites: []
evidence: []
boundaries: []
~~~

primary_question 只写一个问题。reader_outcome 必须能被读者测试验证，不能写成“了解系统”这类无法观察的结果。

## 完稿自检

- 文章开头直接给出问题、适用版本和读者结果。
- 每一节都为主问题增加新的理解或证据。
- 事实、推断、建议和未知有清楚标记。
- 机制文章至少追踪一次输入、状态变化、拥有者、输出和失败处理。
- 选择页保留比较维度，机制细节放在对应独立文章。
- 示例包含版本、前置条件、输入和可观察结果。
- 文章末尾提供下一步和固定版本的官方入口。
